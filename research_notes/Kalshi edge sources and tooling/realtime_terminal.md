# Realtime "Bloomberg-terminal-like" System for Prediction Markets — Architecture & Build Guide

## Kalshi's realtime market data: WebSocket API, channels, auth, rate limits, and can it be streamed without an account?

### Takeaway
Kalshi has an official, documented WebSocket API (`docs.kalshi.com`) with separate public market-data channels (ticker, trade, orderbook, market lifecycle) and private user channels (fills, positions, orders). Every WebSocket connection — including for public channels — must complete API-key authentication (RSA-PSS signed headers) during the HTTP handshake, so market data cannot be streamed without a Kalshi account/API key. REST rate limits are tiered (Basic 200 read/100 write tokens/sec up to Prestige at 10,000/8,000), but the docs did not surface an explicit *websocket message-rate* limit — only a connection-count cap (default 200 concurrent connections/account, tier-scaled) and a "subscription buffer overflow" error code, implying a per-connection backpressure limit exists but isn't numerically documented.

### Cited Findings
- Kalshi's WebSocket connection URLs: production `wss://external-api-ws.kalshi.com/trade-api/ws/v2` and demo `wss://external-api-ws.demo.kalshi.co/trade-api/ws/v2`, with legacy endpoints (`wss://api.elections.kalshi.com/trade-api/ws/v2` and `wss://demo-api.kalshi.co/trade-api/ws/v2`) still supported — [Kalshi Docs: Quick Start WebSockets](https://docs.kalshi.com/getting_started/quick_start_websockets)
- Two independent sources (one referencing the current docs, one an older community reference) disagree on which host is "current" — the newer fetch names `external-api-ws.kalshi.com` as primary with `api.elections.kalshi.com` as legacy; the older community doc (`eishan05/kalshi-agent-skills`) lists `api.elections.kalshi.com` as primary. **Treat `external-api-ws.kalshi.com` as the current endpoint per the live docs.kalshi.com fetch, and confirm against `docs.kalshi.com` again immediately before implementation** since Kalshi has evidently migrated hosts before — [Kalshi Docs](https://docs.kalshi.com/getting_started/quick_start_websockets) vs. [eishan05/kalshi-agent-skills websocket.md](https://github.com/eishan05/kalshi-agent-skills/blob/main/websocket.md)
- Every WebSocket connection requires three auth headers at handshake: `KALSHI-ACCESS-KEY` (API key ID), `KALSHI-ACCESS-SIGNATURE` (RSA-PSS signature), `KALSHI-ACCESS-TIMESTAMP` (unix ms). The signed string follows the pattern `timestamp + "GET" + "/trade-api/ws/v2"` — [Kalshi Docs](https://docs.kalshi.com/getting_started/quick_start_websockets); [eishan05/kalshi-agent-skills websocket.md](https://github.com/eishan05/kalshi-agent-skills/blob/main/websocket.md)
- Public (market-data) channels — `ticker`, `trade`, `market_lifecycle_v2`, `multivariate_market_lifecycle`, `multivariate`, and `orderbook_delta`/orderbook feed — ride the same authenticated session but have no additional per-channel authorization check. Private channels — `fill`, `market_positions`, `communications`, `order_group_updates`, `user_orders` — require the authenticated session and return user-specific data — [Kalshi Docs](https://docs.kalshi.com/getting_started/quick_start_websockets); [eishan05/kalshi-agent-skills websocket.md](https://github.com/eishan05/kalshi-agent-skills/blob/main/websocket.md)
- Orderbook mechanics: subscribing sends an initial `orderbook_snapshot` (full book as arrays of `[price, quantity]` pairs for yes/no sides), followed by `orderbook_delta` messages carrying the price level that changed and a signed quantity delta (positive = added, negative = removed). The orderbook channel only supports `market_ticker`/`market_tickers` filters, not `market_id`/`market_ids` — [Kalshi Docs](https://docs.kalshi.com/getting_started/quick_start_websockets); [eishan05/kalshi-agent-skills websocket.md](https://github.com/eishan05/kalshi-agent-skills/blob/main/websocket.md)
- Subscribe command shape (confirmed by two sources, one shows `market_ticker`, the other `market_tickers` — likely both singular/plural filter keys exist depending on channel):
  ```json
  {"id": 1, "cmd": "subscribe", "params": {"channels": ["ticker"], "market_tickers": ["TICKER-1", "TICKER-2"]}}
  ```
  Command names include `subscribe`, `unsubscribe`, `list_subscriptions`, `update_subscription`. Server responses include `subscribed`, `ticker`, `orderbook_snapshot`, `orderbook_delta`, and `error` message types. Error format: `{"id": 123, "type": "error", "msg": {"code": 2, "msg": "Params required"}}` — [Kalshi Docs](https://docs.kalshi.com/getting_started/quick_start_websockets); [eishan05/kalshi-agent-skills websocket.md](https://github.com/eishan05/kalshi-agent-skills/blob/main/websocket.md)
- The server sends heartbeat pings roughly every 10 seconds with body `"heartbeat"` — [eishan05/kalshi-agent-skills websocket.md](https://github.com/eishan05/kalshi-agent-skills/blob/main/websocket.md) (unverified against the live docs.kalshi.com page directly — treat as likely-correct but not independently confirmed from the primary source in this pass)
- Max concurrent WebSocket connections per account defaults to 200 and scales with account tier — [eishan05/kalshi-agent-skills websocket.md](https://github.com/eishan05/kalshi-agent-skills/blob/main/websocket.md)
- REST rate-limit tiers (tokens/sec, read/write): Basic 200/100, Advanced 300/300, Expert 600/600, Premier 1,000/1,000, Paragon 2,000/2,000, Prime 4,000/4,000, Prestige 10,000/8,000. Most requests cost 10 tokens by default (see `GET /account/endpoint_costs` for exceptions). A rate-limited request returns HTTP 429 with no cooldown penalty — the bucket just needs to refill — [Kalshi Docs: Rate Limits and Tiers](https://docs.kalshi.com/getting_started/rate_limits)
- Recommended usage pattern from third-party guides: use REST for discovery, snapshots, order placement/cancellation, positions, and fill reconciliation; use the authenticated WebSocket for live orderbook, trade, market-status, and fill updates — [botforkalshi.com Kalshi API Tutorial](https://www.botforkalshi.com/blog/kalshi-api-tutorial)
- One practitioner blog specifically covers exponential backoff and reconnect patterns for Kalshi's websocket in Python — [Predict & Profit: Surviving Kalshi API Rate Limits](https://predictandprofit.io/blog/kalshi-api-rate-limits) (not fetched in full this pass; noted as a source worth reading directly before implementation)

### Inferences
- Because auth is required even for public/market-data channels, a Kalshi account and API key (which the existing repo already has, per `src/kalshi/auth.py`/`client.py`) is a hard prerequisite — there is no anonymous firehose to tap.
- The documented REST tier limits are generous enough (Basic = 200 read tokens/sec, ~20 requests/sec at 10 tokens/request) that a REST-polling fallback for a handful of markets remains viable as a backstop if the websocket connection drops, without needing a tier upgrade.
- The disagreement between current and legacy WS hosts, plus the unverified heartbeat interval, means the build should include a config-level WS URL (not hardcoded) and should re-check `docs.kalshi.com/getting_started/quick_start_websockets` at implementation time.

### Gaps
- No explicit websocket message-rate or per-connection subscription-count limit was found in the fetched docs (only account-level connection-count and a generic "subscription buffer overflow" error code) — worth testing empirically or asking Kalshi support before subscribing to more than a few dozen markets on one connection.
- Did not verify the exact JSON field name divergence (`market_ticker` singular vs. `market_tickers` plural) against a single authoritative source in the same fetch — the two fetches returned different examples for different channels, which may simply reflect that orderbook uses singular list semantics differently than ticker; verify directly in the docs' channel-by-channel reference before coding.
- Did not confirm whether Kalshi publishes a formal SLA/uptime figure for the websocket infrastructure.

## Open-source prior art: finance terminals/dashboards (OpenBB) and prediction-market-specific dashboards

### Takeaway
OpenBB Terminal (the CLI/TUI Bloomberg-alternative) was sunset in 2025/2026 in favor of the OpenBB Platform (a Python SDK/API layer) and commercial Workspace/Terminal Pro products, but the full stack was open-sourced under a permissive license — so a solo developer can reuse its data-connector and charting-widget patterns but there is no first-party OpenBB prediction-market module to build on. Purpose-built Kalshi/Polymarket dashboards do exist on GitHub (e.g., "homerun"/"Callisto", "dual-market-trader", "Kalshi-Poly"), but several of these show suspicious duplication across unrelated accounts with identical descriptions, so their provenance and quality should be treated with real skepticism rather than adopted wholesale.

### Cited Findings
- OpenBB Terminal was discontinued because it consumed disproportionate resources (500+ Python package dependencies, installer/maintenance burden, constant vendor API churn) while serving only 7,000–10,000 monthly active users, and because OpenBB didn't own the underlying data rights so monetizing the free terminal directly wasn't viable — [OpenBB: Sunsetting OpenBB Terminal](https://openbb.co/blog/sunsetting-openbb-terminal-why-how-and-what-now/)
- The Terminal's replacement is the OpenBB Platform CLI (a lighter command-line wrapper, no session state like "load AAPL", pip-installable extensions) plus commercial products (Terminal Pro, Excel Add-in, Workspace); the full suite was later open-sourced under a permissive license, so the codebase — data connectors, PyWry-based interactive charting/widgets, the Platform's standardized data-access architecture — is available to fork and adapt — [OpenBB: Sunsetting OpenBB Terminal](https://openbb.co/blog/sunsetting-openbb-terminal-why-how-and-what-now/); [GitHub: OpenBB-Terminal-Desktop/OpenBB-Terminal](https://github.com/OpenBB-Terminal-Desktop/OpenBB-Terminal)
- Web search surfaced no OpenBB-specific prediction-market data extension or menu; OpenBB's own materials describe equities/crypto/options/economic-indicator coverage plus an ML "prediction" (forecasting) menu — unrelated to prediction markets as an asset class — [OpenBB Terminal overview searches, no prediction-market extension found]
- Purpose-built dashboards found on GitHub:
  - **homerun** (`braedonsaunders/homerun`) — FastAPI + PostgreSQL (async) backend, React 19/TypeScript frontend, Docker Compose, Redis, Alembic, WebSocket live feeds; claims 16 background workers for market/news/weather/crypto ingestion across Polymarket, Kalshi, Binance; strategy framework with `detect`/`evaluate`/`should_exit`; Cox proportional-hazards fill models; walk-forward backtesting; L2 order-book replay; AGPL-3.0 license; 179 stars / 38 forks / 2,458 commits at time of fetch — [GitHub: braedonsaunders/homerun](https://github.com/braedonsaunders/homerun)
  - **Callisto** (`m76xx4qmfd-code/Callisto`) and a second **homerun** fork under `systemkiki2026-glitch/homerun` — both carry an *identical* description to `braedonsaunders/homerun` ("Open-source prediction market trading platform for Polymarket & Kalshi... 25+ built-in strategies, copy trading, AI scoring, real-time dashboard. One-click setup.") but under unrelated account names — [GitHub search results, kalshi/polymarket dashboard query]
  - **dual-market-trader** (`rohilkanwar/dual-market-trader`) — Dual-venue Kalshi + Polymarket paper-trading scaffold with settlement gates and a scoreboard dashboard — [GitHub: rohilkanwar/dual-market-trader](https://github.com/rohilkanwar/dual-market-trader)
  - **Kalshi-Poly** (`klinsman0805/Kalshi-Poly`) — Flask dashboard with weather/copy-trade/scalping panels plus Kalshi market discovery and websocket feeds — [GitHub: klinsman0805/Kalshi-Poly](https://github.com/klinsman0805/Kalshi-Poly)
  - A Bitcoin-hourly cross-venue arbitrage bot with a real-time dashboard at localhost:3000 — [GitHub: CarlosIbCu/polymarket-kalshi-btc-arbitrage-bot](https://github.com/CarlosIbCu/polymarket-kalshi-btc-arbitrage-bot)
  - Roundup/listicle sources claim "30+" open-source Kalshi bot projects exist as of 2026 — [botforkalshi.com: Open-Source Kalshi Bot Ecosystem](https://www.botforkalshi.com/blog/open-source-kalshi-bot-ecosystem); [alphascope.app: Best Kalshi Trading Bots on GitHub](https://www.alphascope.app/blog/kalshi-trading-bot-github)

### Inferences
- The identical marketing-style description text ("25+ built-in strategies, copy trading, AI scoring, real-time dashboard. One-click setup.") appearing verbatim across at least three differently-named GitHub accounts (`braedonsaunders`, `m76xx4qmfd-code`, `systemkiki2026-glitch`) is a strong signal of either (a) one operator running multiple accounts/mirrors to farm stars/SEO, (b) a paid template being resold under different names, or (c) a low-effort AI-generated boilerplate being republished — none of which inspires confidence in the claimed feature set even where the code (as in `braedonsaunders/homerun`) superficially looks structurally sophisticated (FastAPI/React/Docker, real commit count). **Recommendation: inspect the actual commit history and CI status of any of these repos before trusting or forking them; do not take the "179 stars / 2,458 commits" figure alone as a maturity signal given the duplication pattern.**
- There is no dominant, clearly-trustworthy open-source Kalshi/Polymarket terminal to build on top of — a solo developer is better served building a thin, purpose-specific tool on the existing REST/paper-broker code than adopting one of these multi-thousand-line unaudited platforms wholesale.
- OpenBB's own sunset rationale (dependency bloat, vendor churn, can't monetize because no data ownership) is a direct cautionary tale for scope discipline: a solo builder should resist replicating OpenBB's broad multi-asset ambition and instead keep the terminal narrowly scoped to Kalshi (+ maybe Polymarket) market data.

### Gaps
- Could not verify GitHub star/fork/commit counts independently (relied on a single WebFetch summary of one repo); these numbers can be inflated or the fetch itself could be imprecise — treat as approximate.
- No first-hand code review of any of these dashboards' actual data pipeline correctness (e.g., whether "L2 order-book replay" is honestly point-in-time or has look-ahead bugs) — only descriptions were reviewed, not code.

## UI/TUI/web options for a solo builder: Textual/Rich, Streamlit/Dash/Panel, Grafana+timeseries DB, React+websockets

### Takeaway
For a solo developer building on an existing Python codebase, Textual (built on Rich) is the lowest-friction path to a genuinely "terminal-like" live-updating interface — it natively supports reactive widgets driven by async/websocket data and can run in a real terminal, over SSH, or (via `textual-serve`) in a browser. Streamlit is faster to prototype for tabular/chart views but its rerun-the-whole-script model fights true tick-by-tick streaming; Grafana is the most operationally mature option for time-series visualization and alerting but requires standing up and feeding a proper timeseries datastore, which is more infrastructure than a solo project strictly needs at laptop scale; a custom React+websocket frontend gives the most control and best "Bloomberg feel" but costs the most build time.

### Cited Findings
- Textual is a Python TUI framework built on top of Rich, explicitly aimed at building full-featured, modern-feeling terminal applications with widget-based, reactive architecture — [Real Python: Python Textual](https://realpython.com/python-textual/); [Textual Tutorial](https://textual.textualize.io/tutorial/)
- "If you need multiple screens, data tables, forms, and a modern widget-based architecture, Textual's reactive design patterns will save you months of work compared to lower-level frameworks—it's ideal for dashboards, admin panels, and interactive tools" — [Pi Stack: Python Terminal UI Libraries comparison](https://www.pistack.xyz/posts/2026-07-01-python-terminal-ui-libraries-textual-rich-prompt-toolkit-urwid/)
- Rich's `Live` display feature explicitly supports refreshing parts of the screen for use cases like dashboards showing data from a websocket feed; a Textual app can also be served to a browser via `textual-serve`, which streams UI updates to the browser over websocket — [Real Python: The Python Rich Package](https://realpython.com/python-rich-package/); [Textual blog: Towards Textual Web Applications](https://textual.textualize.io/blog/2024/09/08/towards-textual-web-applications/)
- Streamlit vs. Grafana positioning: "Streamlit is best for quick, Python-powered apps and ML monitoring, while Grafana is for scalable, alert-driven infrastructure and metrics tracking"; Grafana is described as the tool for tracking "uptime, error rates, latency percentiles" with alerting built in, whereas Streamlit apps can be deployed with more flexibility to "start simple and scale up" — [Fastero: Streamlit vs Grafana](https://fastero.com/blog/streamlit-vs-grafana-when-to-use-each) (note: this is a vendor/comparison-site source, not a primary benchmark)
- No specific websocket-latency benchmark numbers comparing Streamlit and Grafana were found in this research pass — search results acknowledged the absence of hard numbers and suggested the asker benchmark independently — [Slashdot: Grafana vs Streamlit 2026 comparison](https://slashdot.org/software/comparison/Grafana-vs-Streamlit/)

### Inferences
- Given the repo already has a paper broker, REST client, and research pipelines in Python, Textual is the most natural fit: it stays in-process with the existing Python code (no separate frontend build, no need to stand up Postgres/Grafana), can subscribe directly to the same asyncio websocket client used for market data, and can be run locally or over SSH to a cheap VPS with zero extra infra.
- Streamlit's execution model (rerun top-to-bottom on each interaction/timer) is workable for a "refresh every N seconds" dashboard of orderbook snapshots, but is a poor fit for true per-message ticker/trade streaming without extra plumbing (e.g., `st.empty()` placeholders polled from a queue) — it's better suited to a secondary/backtest-review view than the live terminal itself.
- Grafana + a timeseries DB (e.g., a lightweight Postgres/Timescale or even a Prometheus pushgateway) is worth adding later specifically for the "operational monitoring" concern (websocket uptime, message lag, reconnect counts) rather than as the primary trading-decision UI — it's the right tool for the *ops dashboard*, not the *research terminal*.
- A custom React+websocket frontend is the highest-effort, highest-payoff-for-portfolio option (see interview-artifact question below) but is not the fastest path to a working research tool; recommend it only as a phase-2 polish step once the Textual version proves the display concepts (orderbook depth, arb ladder, alerts) are useful.

### Gaps
- No hard data found on Textual's rendering performance ceiling (messages/sec it can absorb before UI lag) for a dense orderbook-delta stream — likely fine at "a handful of markets" scale per the stated constraint, but unverified; would need to prototype and measure.
- Dash and Panel (explicitly asked about) were not directly researched with dedicated searches in this pass beyond general awareness; treat their trade-offs as a gap — general knowledge suggests Dash (Plotly) and Panel (HoloViz) sit similar to Streamlit (Python-server-rendered web apps, easier live-chart embedding than Streamlit via `dcc.Interval`/websocket callbacks, more boilerplate than Streamlit) but this was not verified against current docs in this research pass.

## Storage for realtime market data: SQLite/DuckDB/Postgres/Timescale/Parquet at laptop scale

### Takeaway
For a solo project capturing tick/orderbook data from "a handful" to ~50 markets, DuckDB (embedded, columnar, Parquet-native) or plain SQLite are the right-sized choices — no server process, no ops burden — while TimescaleDB's value (partitioning/sharding, retention policies, PostgreSQL ecosystem) is aimed at multi-node production deployments that a laptop/cheap-VPS solo setup doesn't need. Practical data-volume figures for "50 markets for a month" were not found in a primary source in this pass and should be treated as a gap requiring a back-of-envelope estimate.

### Cited Findings
- "DuckDB is an embedded database designed to execute analytical SQL queries fast while embedded in another process," whereas "TimescaleDB is a time-series database built on top of PostgreSQL" with automatic partitioning/sharding for distributed, multi-node scale — [StackShare / db-engines comparison summary](https://stackshare.io/stackups/duckdb-vs-timescaledb)
- "DuckDB can be used effectively with time series data, supporting processing and analyzing tabular datasets through CSV or Parquet files with an optimized analytics engine... well-suited for lightweight, local storage of orderbook snapshots on a laptop," while "TimescaleDB would be better suited for multi-node production deployments rather than local laptop storage, given its PostgreSQL-based infrastructure and operational complexity" — [pythondataengineering.net: DuckDB vs TimescaleDB](https://pythondataengineering.net/compare/duckdb-vs-timescaledb)
- "DuckDB does not have extensive time-series functionality built-in and primarily focuses on efficient columnar storage and analytical query performance" — meaning time-bucketing/downsampling helpers that Timescale provides natively (e.g., `time_bucket()`) would need to be hand-rolled in DuckDB SQL — [pythondataengineering.net: DuckDB vs TimescaleDB](https://pythondataengineering.net/compare/duckdb-vs-timescaledb)

### Inferences
- Given the existing repo already uses a SQL schema (`src/db/schema.sql`, SQLite implied by `database.py` patterns typical of this project style) and a paper-broker schema (`src/paper/schema.sql`), the lowest-friction extension is to keep using SQLite (or migrate the tick/orderbook-specific tables to DuckDB if analytical query speed over months of accumulated Parquet-style data becomes the bottleneck) rather than introducing Postgres/Timescale, which would add a server process, credentials, and backup burden disproportionate to "a handful of markets on a laptop."
- A reasonable architecture: write raw websocket messages (ticker/trade/orderbook_delta) append-only to a local log (JSONL or Parquet, partitioned by day/market) as the durability layer, then periodically materialize into SQLite/DuckDB tables for query (best-bid/ask, mid, spread, imbalance) that the terminal reads — this decouples "never lose a message" from "queryable state" and makes historical replay (for backtesting) straightforward since Parquet files are naturally point-in-time-ordered.
- Back-of-envelope volume estimate (not sourced, offered as an inference/order-of-magnitude only): a moderately active Kalshi market might produce on the order of a few ticker updates and a handful of orderbook deltas per second during active trading and much less overnight; for 50 markets over a month, this is very plausibly in the low-tens-of-millions-of-rows range for orderbook deltas and comparable or less for trades/ticker — likely a few GB/month uncompressed JSON, dropping substantially (often 5–10x) if written as compressed Parquet/DuckDB columnar storage. **This estimate is not sourced and should be validated by instrumenting the actual feed for a day and extrapolating**, since Kalshi market activity is extremely uneven across markets (a hot NFL game market vs. a quiet long-dated economic market differ by orders of magnitude).

### Gaps
- No primary source (Kalshi docs, a published engineering blog, or a benchmark) was found giving actual observed message-rate or byte-volume figures for Kalshi's websocket feeds at any market count — this is the single biggest unverified assumption in the storage section and should be treated as a measurement task (capture real traffic for a day, then extrapolate) rather than a researched fact.
- Did not find benchmark numbers for DuckDB write throughput under a continuous streaming-insert workload (DuckDB is optimized for bulk/analytical loads, not necessarily high-frequency single-row inserts) — a real implementation should batch inserts (e.g., buffer N seconds or messages before a DuckDB/SQLite transaction) rather than insert per-message, which is a widely known SQLite/DuckDB performance pattern but wasn't specifically benchmarked here for this workload.

## What a prediction-market terminal should actually display (research tool, not decoration)

### Takeaway
The de facto "must-have" set — order book depth/imbalance, spread, model-vs-market probability, bracket-ladder sum-to-1 arbitrage checks, time-to-close, volume/open-interest, and settlement-status — is well-grounded in both general market-microstructure practice and prediction-market-specific literature on arbitrage; Kalshi's own websocket channels (`ticker`, `orderbook_delta`/snapshot, `trade`, `market_lifecycle_v2`) map directly onto most of these display needs, meaning the terminal is largely a presentation/alerting layer over data Kalshi already streams.

### Cited Findings
- The core arbitrage logic for bracketed/mutually-exclusive markets: "When a set of prices that must logically sum to $1.00 does not, a trader can buy the mispriced combination and collect the guaranteed dollar regardless of the result" — and concretely, summing every leg of a bracket (example given: 79 + 18.4 + 0.9 + 0.4 + 0.2 = 98.9¢) shows an arbitrage if the total is under $1.00 (or over, on the short side) — [Elite Trader: The Math Behind Prediction Market Arbitrage](https://www.elitetrader.com/et/threads/the-math-behind-prediction-market-arbitrage.390524/); [clawarbs.com: Prediction Market Arbitrage](https://clawarbs.com/blog/prediction-market-arbitrage/)
- The correct check uses bid/ask, not last-price: "if the sum of bid prices exceeds $1.00 or if the sum of ask prices are below $1.00, arbitrageurs have an opportunity to secure risk-free profit" — i.e., the arb check should be run separately on the sum of best-asks (buy-the-basket check, should be ≥ $1.00 if no arb) and the sum of best-bids (sell-the-basket check, should be ≤ $1.00 if no arb) — [Elite Trader](https://www.elitetrader.com/et/threads/the-math-behind-prediction-market-arbitrage.390524/)
- Fees matter: "even when applying fees (approximately 2% on the winning position on platforms like Polymarket), gross edges often become net losses after transaction costs" — meaning any arbitrage alert in the terminal needs a fee-aware threshold, not just a raw sum-vs-$1 check — [Elite Trader](https://www.elitetrader.com/et/threads/the-math-behind-prediction-market-arbitrage.390524/) (note: Kalshi's own fee schedule differs from Polymarket's; the repo's own commit history — `fix(research): charge Kalshi's fee once per order, not per contract` — shows this fee-modeling nuance is already understood in this codebase and should be reused directly rather than re-derived)
- Kalshi's `market_lifecycle_v2` websocket channel streams market state transitions (created, activated, determined, settled, etc.), which directly supports a "settlement-source status" display without needing a separate polling loop — [Kalshi Docs / eishan05 websocket.md, per Key Questions section above]
- `ticker` channel messages include bid-ask spread, last trade price, and open interest; `trade` messages include trade ID, price, contract count, and taker side — both are direct inputs to volume/OI and spread displays — [eishan05/kalshi-agent-skills websocket.md](https://github.com/eishan05/kalshi-agent-skills/blob/main/websocket.md)

### Inferences
- Orderbook imbalance (sum of bid depth vs. ask depth near the touch) is a standard, well-understood microstructure signal not specific to prediction markets, and is directly computable from the `orderbook_snapshot`/`orderbook_delta` messages already documented above — no additional data source is needed.
- "Model probability vs. market-implied probability" is the one display element that depends entirely on the reader's own existing research pipeline (`src/research/`, `src/models/`) rather than on any new data feed — the terminal's job here is purely to render the reader's own model output next to the live market mid-price, so this is a UI/plumbing task, not a data-acquisition task.
- Time-to-close is derivable from market metadata already available via Kalshi's REST market-detail endpoint (close_time field, standard on Kalshi markets) — likely already surfaced by the existing REST client in `src/kalshi/client.py`, so no new integration is required, only display.
- A useful "alert" layer is a small rules engine evaluated on every relevant websocket message: (a) bracket sum-to-1 breach beyond fees, (b) spread widening beyond a threshold (possible stale/thin book), (c) model-vs-market divergence beyond a threshold, (d) market entering `determined`/`settled` lifecycle state. This requires no new infrastructure beyond what's already planned — it's a callback attached to the message-processing loop.

### Gaps
- Did not find prediction-market-specific research quantifying "how much orderbook imbalance predicts short-term price movement" for Kalshi specifically (as opposed to general equity/crypto microstructure literature) — if this matters for the reader's model, it would need dedicated research beyond this pass's scope.
- Did not verify whether Kalshi's REST/WS API exposes an explicit "settlement source" field (e.g., which data provider/rule resolves a market) distinct from lifecycle state — the `market_lifecycle_v2` channel covers state transitions, not necessarily the human-readable settlement-source metadata; would need to check Kalshi's market-detail REST schema directly.

## Operational concerns: reconnect/backfill, clock discipline, avoiding look-ahead in replay, monitoring

### Takeaway
The reconnect/backfill and monitoring practices for this project are the same well-established patterns used across crypto/equities websocket trading systems generally (exponential backoff with jitter, sequence-number gap detection, REST-snapshot-then-WS-delta reconciliation, tracking message age/lag/reconnect-count); clock discipline for a solo research tool needs NTP-level accuracy (not GPS/PTP, which is an institutional HFT requirement), and avoiding look-ahead bias in replay comes down to one disciplined rule: only ever feed the backtest data that was time-stamped as received at or before the simulated decision instant.

### Cited Findings
- "Reliable WebSocket handling requires three layers: reconnection (get connection back), gap detection (know if you missed messages), and state recovery (fix state if you did)" — [DEV Community: WebSocket Reconnection That Actually Works](https://dev.to/matrixtrak/websocket-reconnection-that-actually-works-auto-reconnect-guide-for-trading-bots-3fe0)

### Inferences
- For this solo project, NTP (standard OS-level time sync, e.g., macOS/Linux's built-in `timed`/`chronyd`/`systemd-timesyncd`) is fully sufficient — PTP/GPS stratum-1 hardware is an institutional HFT concern irrelevant at "research terminal for a handful of markets" scale. The practical requirement is simply: timestamp every received message with local receipt time in UTC (not just trust the exchange-provided timestamp, in case of exchange-side clock skew), and store both.
- Kalshi's websocket messages likely carry either a sequence number or a server timestamp (not explicitly confirmed as a field name in the fetched docs excerpts above) — if a `seq` field exists, gap detection is straightforward; if not, the fallback pattern is periodic full REST snapshot reconciliation (e.g., every N minutes, fetch the REST orderbook and diff against the locally-maintained book state) as recommended generally above.
- The single most important discipline for this project's own backtesting (given the repo already has a "maker simulation" and "weather backtest" per its commit history) is: when replaying stored ticker/trade/orderbook logs to evaluate a strategy, the "decision" logic must only see messages up to and including the simulated "now" timestamp, and any simulated order fill must be matched against orderbook state that existed *after* the decision was formed (i.e., don't let a simulated order "fill" against a book snapshot the decision itself was computed from — insert at least one message's worth of latency) — this generalizes the "decision day vs. trade day" separation cited above to a tick-level replay setting.
- Recommended minimal monitoring dashboard/log fields for this project: last-message-received timestamp per subscribed market, current reconnect count, count of detected sequence gaps (or snapshot-reconciliation diffs) since start, and end-to-end message age (receipt time minus exchange-reported time, if available) — these can be exposed as a Textual panel or a simple Grafana panel fed by a Prometheus-style local metrics file, whichever the builder already prefers.
